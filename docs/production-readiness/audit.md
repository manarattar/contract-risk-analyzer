# Evidence-based audit

Date: 2026-09-09. Baseline and preservation details: [README](README.md). Line references below are repository-relative paths at the reviewed working tree. Ranges identify the supporting implementation, not runtime observations.

## Assessment and strengths

The project is a useful workflow demonstrator with separable parser, splitter, analyzer, vector, comparison and report services. Pydantic models constrain output shape and score bounds (`backend/app/schemas.py:33-83`). Upload extensions are allowlisted and a post-read size limit exists (`backend/app/routers/upload.py:19-20,71-77`). Q&A checks that a document is complete (`backend/app/routers/qa.py:21-25`). Per-document vector collections reduce accidental unscoped searching (`backend/app/services/vector_store.py:15-17,37-44`), but do not authorize access. Original chunk text is assigned by application code rather than trusted from the model (`backend/app/services/risk_analyzer.py:424-426`). UI and reports contain legal-advice disclaimers. Unit tests cover parsing model JSON, score helpers, mock schemas and in-memory report generation.

These strengths are a starting point. A disclaimer cannot compensate for fabricated answers, omitted evidence or unsupported signing recommendations.

## Evidence classes and severity

- **Verified:** directly observed source behavior or recorded safe check. A code-path finding does not prove successful exploitation or production configuration.
- **Potential risk:** plausible consequence requiring a runtime/adversarial test or environmental verification.
- **Recommendation:** proposed design/control, not something already implemented.
- **Assumption/hypothesis:** proposed operating context requiring stakeholder validation.
- **Critical:** plausible cross-user disclosure or materially misleading review central to product purpose. **High:** major fidelity, safety, availability or lifecycle gap. **Medium:** substantial usability/operational limitation. Priorities in the backlog also reflect sequencing.

## Actual workflow and endpoint ownership

All routes depend at most on a database session; there is no principal/owner dependency. Models have no owner or workspace column (`backend/app/database.py:14-43`). UUIDs are identifiers, not authorization.

| Step / API | Verified implementation | Authentication / ownership and outcome |
|---|---|---|
| Upload `POST /api/upload` | Extension check, full read, local write, SQLite document, BackgroundTasks (`backend/app/routers/upload.py:65-95`) | None; any caller reaching API can consume storage and processing |
| Processing/status `GET /api/status/{id}` | parse → split → mock/live analyze → Chroma → SQLite (`backend/app/routers/upload.py:28-62,98-107`) | None; raw exception string returned as error message |
| Review `GET /api/analysis/{id}` | First analysis JSON row by document ID (`backend/app/routers/analysis.py:11-16`) | None; results keyed only by ID |
| Questions `POST /api/qa` | Document exists/complete → top four chunks → canned or LLM answer (`backend/app/routers/qa.py:19-44`) | None; document ID controls retrieval scope |
| Compare `POST /api/compare` | Two new files, parallel full analyses, first clause per type, score deltas (`backend/app/routers/compare.py:29-72,75-123`; `backend/app/services/comparison_service.py:17-65`) | None; bypasses Document records and vector indexing; successful/failing worker attempts to remove both originals |
| Comparison status/result | DB lookup by comparison ID (`backend/app/routers/compare.py:126-145`) | None; stored analyses contain original text |
| Export `GET /api/report/{id}` | Read DB → in-memory ReportLab PDF (`backend/app/routers/report.py:12-30`) | None; no review approval/provenance record |
| Library/original pages/decisions | No corresponding API in router inventory; App uses transient state (`backend/app/main.py:26-30`; `frontend/src/App.jsx:15-27,70-76,270-296`) | Absent |
| Deletion | No DELETE route or purge service in inspected source; original upload persists, vectors persist, JSON persists | Absent; compare worker cleanup is partial lifecycle cleanup, not user deletion |

## Scope-specific observations

There is no evidence of a global vector query: current retrieval selects a document collection. The security problem is that the caller is not authorized for that document; arbitrary cross-document retrieval is not asserted. No app-level encryption-at-rest configuration was found; host/disk encryption remains unknown. SQLAlchemy query expressions are parameterized; this audit does not allege SQL injection.

The UI already adapts some grids with Tailwind breakpoints and lets upload users browse instead of dragging. Comparison retains fixed multi-column structures and the clause table scrolls horizontally; mobile layout quality is a source-based concern pending viewport testing. No color contrast ratio or Core Web Vitals result is claimed.

Missing pages cannot always be detected from a file alone: page-number discontinuities or referenced schedules can raise warnings, but completeness requires user confirmation. Absence of an extracted clause does not establish legal absence.

## Checks and limitations

Recorded results and exact safe commands are in [evaluation-and-test-plan.md](evaluation-and-test-plan.md). No packages installed; no application server, migration, build/deploy, live LLM, vector-model download or uploaded document processing was run. Existing backend unit tests use synthetic in-memory mock report data. `.env`, local databases, Chroma data and existing PDF/TXT contracts were deliberately not opened.

Production identity provider, proxy, encryption, region, provider contract, telemetry, backups and network access remain unverified. No penetration testing, malware execution, screen-reader session, browser rendering of the application, live retrieval benchmark or legal adjudication was performed. Recommendations use [primary sources](sources.md); these are design baselines, not certification.
